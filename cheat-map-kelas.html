CHEAT MAP • FOR THE MUTATOR

Bug Classes per Lane,
Derivatives, Lenses & Chaining

One file for picking a priority angle before mutate. Pick a lane, pick max 3 classes, and the mutator writes the variants.

1. How to use

1

Pick a lane

A lane is the project type: web2, web3-contract, or wallet. The lane sets which classes you can pick.

2

Pick max 3 classes

From that lane, pick the max 3 classes with the highest impact on this project. 1-2 classes is ideal, 3 classes is the ceiling.

3

Write it into the threat model

Write the class name exactly into the Priority angle section. The mutator reads the name and selects the lenses automatically.

The easy formula (2 classes)
Each bug theme has 2 to 5 hunting methods. Pick 2 themes and the methods merge into one set. A method shared by both themes counts once.

1. Merge the hunting methods from both themes, drop the duplicates. Usually 5 to 10 methods.
2. Multiply by 3. Each method becomes 3 question versions.

So 2 themes usually become 15 to 30 questions. Worked example: theme A has 5 methods, theme B has 5, 1 shared. Total methods = 5 + 5 - 1 = 9. Questions = 9 times 3 = 27.

2. Lenses 1-13: how to hunt bugs

A lens is an angle for hunting bugs. One bug class is usually hunted with several lenses. This is the full list, in plain language.

L01Missing enforcementThere should be a check, but there is none at all.
L02Enforced here, assumed thereChecked on path A, not checked on path B to the same action.
L03Unchecked assumptionThe app trusts outside data without checking it.
L04Undocumented behavior dependencyCode relies on library or system behavior that is not guaranteed.
L05Unsafe compositionSafe one by one, dangerous combined.
L06Same object, different permissionsOne object is reachable through many paths, with different permissions on each.
L07Identity rebindingThe owner or identity of an object can change without a proper check.
L08Failed request, real side effectA request is rejected, but something still changes or gets sent.
L09Order-dependent checkIf a step is skipped or reversed, the check is skipped too.
L10Failed transaction, lingering effectA transaction is cancelled, but a side effect does not roll back with it.
L11Access after delete or revokeSomething deleted, logged out, or revoked can still be used.
L12Unauthorized undoA change can be undone by someone who should not be allowed to.
L13Contradictory dual stateOne object can sit in two opposing states at the same time.
Easy to mix up? L01 means no check at all. L02 means the check exists but only on one path. L03 means data is trusted without a check. L08 is a failed request, L10 is a cancelled transaction.

3. Lane A - web2

6 classes. The highest class in general: Tenant isolation & IDOR. If the project is mostly about money, Business logic payment can move up to number 1.

Lane A - web2

Apps and APIs: accounts, payments, files, and workflows.

A1. Tenant isolation & IDOR

tenant-isolationL01L02L03L06L07L11

Invariant: user A cannot read, change, or delete what belongs to user B.

Derivatives:

  • IDOR / BOLA: change the ID in the request, get objects owned by another tenant.
  • BFLA: admin endpoints callable by a plain role.
  • Mass assignment: owner or role fields can be set through the request body.
  • IDOR through another path: safe in the UI, open through an old API, export, or preview.
  • Objects still accessible after revoke or tenant move.
Chain: another tenant's data → Auth / ATO → admin functions.

A2. Business logic: payment / pricing / payout

payment-logicL03L05L09L10L13

Invariant: money only moves by the business rules. Totals, prices, and destinations cannot be changed one-sidedly. One payment, one benefit.

Derivatives:

  • Prices, discounts, or fees computed on the client and then trusted by the server.
  • Payout or refund destination changed to an attacker account.
  • Quota, budget, or trial used past the limit.
  • Approve, verify, or pay steps skipped.
  • One payment, coupon, or claim used 2 times.
  • Amount, currency, or decimals manipulated.
Chain: logic flaw + race → double spend. Logic flaw + IDOR → someone else's payout.

A3. Auth, session & privilege escalation

auth-sessionL01L02L07L11

Invariant: only the rightful account owner or role can act. Sessions and tokens die after logout, revoke, or password change.

Derivatives:

  • Takeover through password reset: token guessable, reusable, or usable on another account.
  • Old session still works after password change or logout.
  • Role changed through body, cookie, or token, then a high-role endpoint becomes callable.
  • The 2FA step can be skipped through another endpoint.
  • An account can be linked to an attacker account without owner verification.
Chain: Auth / ATO → Tenant isolation → admin functions.

A4. File upload / download & access

file-handlingL01L06L08L12

Invariant: files are only accessible to their owner. An uploaded file cannot become code or leave the allowed folder.

Derivatives:

  • IDOR download: change the file ID, download someone else's file.
  • Path traversal: leave the allowed folder through the file name.
  • Dangerous upload: file type checked in the UI only, file becomes XSS or RCE through a parser.
  • SSRF through a file: file URL or metadata makes the server fetch an internal URL.
  • A failed or rejected file is still stored and accessible.
Chain: upload → XSS / RCE. Download IDOR → Tenant isolation.

A5. Workflow / state-machine bypass

workflow-stateL05L09L10L12L13

Invariant: state only moves through allowed transitions, in the right order, by the right role.

Derivatives:

  • Approval, review, or verification steps skipped.
  • Cancel or undo by an unauthorized party.
  • A failed transaction still leaves side effects.
  • Status in the database differs from status in another service, and the gap is usable.
  • Two actions that are safe alone combine into a bypass.
Chain: workflow skip + race → double benefit. Workflow skip → payment logic.

A6. Integration / webhook / OAuth

integrationL02L03L04L06

Invariant: events or tokens from an integration are only trusted when their origin is verified. One integration cannot act for another tenant.

Derivatives:

  • Webhook with no signature verification: fake events change status or payments.
  • OAuth redirect or token used across accounts or tenants.
  • Integration payloads trusted without validation.
  • Old integration endpoints with looser checks than the main endpoint.
Chain: fake webhook → workflow bypass. OAuth → Auth / ATO.

4. Lane B - web3-contract

6 classes. The highest class in general: Settlement accounting. Funds out cannot exceed funds in.

Lane B - web3-contract

Smart contracts: settlement, oracles, attestations, and execution.

B1. Settlement accounting: mint / burn / fund conservation

settlement-accountingL01L03L05L10L13

Invariant: total mint is not larger than real deposits. One deposit, one settlement.

Derivatives:

  • Mint without backing: mint with no matching deposit.
  • Double-settle: one deposit settled 2 times.
  • Accounting drift: internal balance differs from the real token balance.
  • Burn or release without a valid check.
  • A deposit sweep lands on the wrong order.
Chain: accounting + attestation replay → drain. Accounting + oracle → settle at the wrong price.

B2. Oracle / price / fee manipulation

oracle-pricingL03L04L09L13

Invariant: prices and fees used to settle must be fresh, from a verified source, and not pickable one-sidedly.

Derivatives:

  • Stale prices used because the price age limit is not checked on-chain.
  • A solver-signed price trusted with no on-chain verification.
  • Zero fee, negative fee, or limiter bypassed through another path.
  • Price-impact check uses the wrong price.
Chain: oracle → settlement accounting (cheap settle, expensive claim).

B3. Attestation / signature replay & idempotency

attestation-replayL03L07L09L10

Invariant: one authorization, one execution. A signature cannot be reused across orders, chains, or actions.

Derivatives:

  • Replay across orders: the same signature used for two different orders.
  • Replay across chains: a domain without chainId accepted on another chain.
  • Fake idempotency: different keys but identical economic actions, both succeed.
  • Recipient, amount, or chainId changed without invalidating the signature.
Chain: replay → settlement accounting (double-settle). Replay → executor claiming.

B4. Executor / solver claiming & access

executor-claimL01L02L06L07

Invariant: only the chosen solver or resolver may execute that order. One solver cannot claim another solver's fill.

Derivatives:

  • Resolver not bound: the signature does not bind a specific resolver, anyone can execute.
  • Another solver's fill or reward taken through another execution path.
  • Withdrawal address changeable one-sidedly with no timelock.
  • Another function or contract reaches the same assets with looser checks.
Chain: executor → settlement accounting. Executor → attestation.

B5. Admin / roles & upgrade

admin-rolesL01L07L11L12

Invariant: admin functions are only callable by the admin role. A revoked role cannot be used again. Critical changes are not instant without a timelock.

Derivatives:

  • Admin or config function with no role check.
  • Owner, beneficiary, or delegate can be re-bound to an attacker address.
  • A revoked role or allowance can still be used.
  • Destination, oracle, or critical parameter changed one-sidedly with no timelock.
Chain: admin → all other classes. Admin is the key to accounting, oracle, and executor.

B6. Token behaviour & external calls

token-behaviourL04L05L08

Invariant: the contract must not assume token or third-party behavior that is not guaranteed.

Derivatives:

  • Fee-on-transfer or rebasing: the amount received differs from the amount sent, accounting breaks.
  • Hook or callback: an outside party calls back into the contract mid-execution.
  • Call fails but state already changed.
  • Approve + transfer + mint that are safe alone become dangerous combined.
Chain: token behaviour → settlement accounting.

5. Lane C - wallet

5 classes. The highest class in general: Key & seed. If the key leaks, all funds on all chains are lost.

Lane C - wallet

Wallets on device: keys, signing, backup, and entry paths.

C1. Key & seed

key-seedL01L03L06L11L13

Invariant: no outsider can obtain the private key or recovery phrase. A key is only accessible after auth. A key does not leak through another path.

Derivatives:

  • Plaintext key in a file or log, not in the device's secure storage.
  • Key readable or usable with no PIN or biometric.
  • Key leaked through backup, log, crash dump, clipboard, or screenshot.
  • Key or session not invalidated after logout.
  • Key in device storage differs from the key in cloud backup, and the gap is usable.
  • Key that is safe in the UI but reachable through a deep link, backup restore, or export.
Chain: leaked key → signing abused. Leaked key → all funds on all chains lost.

C2. Signing & transaction display

signingL02L03L05L08L09

Invariant: what the user sees is what actually gets signed. One approval, one displayed action. A signature cannot be reused.

Derivatives:

  • Blind signing: destination and transaction content not shown, user approves blind.
  • Display mismatch: amount, recipient, or network shown differ from what is signed.
  • Permit or typed data: signed fields hidden, domain without chainId replayable across chains.
  • Address poisoning: a lookalike fake address is shown so the user sends to the wrong place.
  • Amount, recipient, or fee changed after the review screen but before signing.
  • Request fails but the signing prompt still appears.
Chain: signing → key (if signing runs without proper auth). Signing → entry paths (a malicious request comes in through a dApp).

C3. Auth, recovery & backup

auth-recoveryL01L03L06L11

Invariant: backup, export, and recovery only run after re-auth. The recovery phrase does not leak. Revoked auth cannot be used again.

Derivatives:

  • Backup exported from an unlocked device with no PIN or biometric.
  • Weak backup encryption, minimum password with no strength check, backup file openable offline.
  • A 6-digit PIN guessable offline because throttling is only in the app, not in hardware.
  • Seed shown or kept in memory or storage with no protection.
  • Imported backup overwrites the victim wallet with no check.
Chain: leaked backup → key & seed. Auth bypass → signing.

C4. Entry paths: deep link / QR / WebView / WalletConnect

entry-pathsL02L03L05L06

Invariant: outside requests only run when their origin and content are verified. One entry path must not have looser checks than another path.

Derivatives:

  • Deep link abuse: deep links used to inject a signing request or change state.
  • Malicious QR payload: a QR code holds a recovery, private key, or WalletConnect URI that executes directly.
  • WebView or JS bridge: bridge exposed to web content, XSS in the WebView can reach wallet functions.
  • WalletConnect: session or signing request from a malicious dApp, origin check anchored to an attacker-claimed URL.
  • Social login or connect: origin spoof, login used for access it was not meant for.
Chain: entry path → signing (a malicious request gets approved). Entry path → key (recovery or private key payload).

C5. Platform & supply chain

platform-supplyL04L06

Invariant: a website or dependency must not become a path into the wallet. Unassumed dependency behavior must be proven to matter for this project, not just by version.

Derivatives:

  • Website IDOR or session: an account on the website can access another account's data.
  • Dependency used dangerously: RNG or KDF in an unverifiable binary, an SDK trusted without a check.
  • Undocumented SDK behavior changes and a check is skipped.
Chain: platform → key / signing if the website or SDK can trigger a wallet action. This class has the lowest priority, drop it first when a run already has 3 classes.

This is the table as requested: which lens hunts each bug technique. A technique is the how of the violation. A class is the what that gets violated. One technique can sit in several classes.

7. Chaining: do not throw away a small finding

Check the chain first before closing a finding. Severity follows the final impact of the chain, not the first link.

API / IDOR→Auth / ATO→RCE
SSRF→RCE→Auth / cloud
XSS→Auth / ATO→API
SQLi→Auth→RCE
Business logic→Race→Double benefit
File upload→XSS / RCE
Host header→Auth / ATO
Oracle→Settlement accounting
Attestation replay→Settlement accounting
Entry paths→Signing→Key & seed
Leaked backup→Key & seed
Chain rule: if one link is proven, do not close it at the first class. Move to the next class in that chain before writing the report.
